# RFC 3986 — generic query-string percent-encoding

Source: [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986), §2 (Characters)
and §3.4 (Query). **This is not a selectable target format in Step 1** — it
defines no comparison operators, no AND/OR, no filter semantics of any
kind, so there's nothing to "convert to." It's purely the character-escaping
mechanism OData and RQL use in Step 7, *on request*, when their
already-built expression needs to be embedded in an actual URL query
string. The expression being encoded always comes from OData's or RQL's own
grammar (`references/odata.md` / `references/rql.md`) — this file never
invents filter syntax of its own, only escapes whatever value it's handed.

## Unreserved characters (never encoded)

> `unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"`

That's `A-Z`, `a-z`, `0-9`, `-`, `.`, `_`, `~` — nothing else. Two encodings
that differ only in an unreserved character represent the same value, so
these are always left as-is.

## Reserved characters (must be encoded when carrying data, not syntax)

> `reserved = gen-delims / sub-delims`
> `gen-delims = ":" / "/" / "?" / "#" / "[" / "]" / "@"`
> `sub-delims = "!" / "$" / "&" / "'" / "(" / ")" / "*" / "+" / "," / ";" / "="`

These characters are meaningful as URI *syntax* (e.g. `&` and `=` separate
query key/value pairs). When a value being carried inside a query string
contains one of them literally, it must be percent-encoded so it isn't
mistaken for syntax.

## Percent-encoding procedure (§2.1)

> `pct-encoded = "%" HEXDIG HEXDIG`

Take the UTF-8 byte sequence of the character; for every byte that isn't an
unreserved ASCII character, emit `%` followed by two hex digits for that
byte's value. **Uppercase hex digits are recommended** (`%3D`, not `%3d`) —
this skill always emits uppercase. Multi-byte UTF-8 characters (e.g. `é` →
`0xC3 0xA9`) are encoded byte-by-byte: `%C3%A9`.

This skill encodes **everything that isn't in the unreserved set** —
including sub-delims like `$`, `'`, `(`, `)` — rather than leaving some
reserved characters raw. That's the safe default for arbitrary key/value
data (as opposed to a full URI where some reserved characters are
intentionally left as structural syntax).

Note: this is **not** the same as `application/x-www-form-urlencoded`
(what `urllib.parse.urlencode` in Python or `URLSearchParams` in
JavaScript/Node produce) — that convention encodes space as `+` instead of
`%20`, and disagrees with plain RFC 3986 on a few characters (notably `~`,
which some form-urlencoded implementations escape and RFC 3986 does not).
The bundled `scripts/encode_query.{py,mjs}` implement RFC 3986 directly, not
form-urlencoding — see the skill's script contract.

## Manual fallback (no script runtime available)

If neither Python nor Node is available, encode by hand using this table:

| Keep as-is | Percent-encode |
|---|---|
| `A`-`Z`, `a`-`z`, `0`-`9`, `-`, `.`, `_`, `~` | everything else, one `%XX` per UTF-8 byte, uppercase hex |

Common encodings you'll need often: space → `%20`, `"` → `%22`, `#` →
`%23`, `$` → `%24`, `&` → `%26`, `'` → `%27`, `(` → `%28`, `)` → `%29`,
`*` → `%2A`, `+` → `%2B`, `,` → `%2C`, `/` → `%2F`, `:` → `%3A`, `;` → `%3B`,
`<` → `%3C`, `=` → `%3D`, `>` → `%3E`, `?` → `%3F`, `@` → `%40`, `[` → `%5B`,
`]` → `%5D`.

## Worked example

This file has no expression syntax of its own to demonstrate — see
`references/odata.md`'s or `references/rql.md`'s "Worked example" section
for the full raw-expression-to-encoded-query-string flow (e.g. OData's
`$filter=(group eq 'student' and age gt 20) or ...` becoming
`%24filter=%28group%20eq%20%27student%27...`). The mechanism itself is just:
take the `[key, value]` pairs the calling format already built, run each
through the table above.
